# RK3506 6.12 Boot Analysis

## Scope

The known-good baseline is the Luckfox Lyra Ultra booting the vendor 6.1 RK3506
kernel. The target is a 6.12 LTS kernel image that boots the same board using the
same Ubuntu rootfs and RK update-image packaging path.

The official Luckfox Lyra SDK documentation identifies the SDK as a Linux 6.1
SDK and maps the Lyra Ultra to the RK3506 board DTS
`rk3506b-luckfox-lyra-ultra.dts` plus `rk3506-luckfox-lyra-ultra.dtsi`. That
matches the local 6.1 reference tree and the stock board's runtime
`/proc/device-tree/compatible` values:

- `rockchip,rk3506g-demo-display-control`
- `rockchip,rk3506`

Luckfox's kernel configuration documentation also calls out the normal Rockchip
SDK rule that module changes require both a kernel rebuild and a rootfs rebuild
so the matching `.ko` files land under `/lib/modules/<kernel-version>/`. That
is why the USB2 PHY module fix was followed by a rootfs rebuild, while later
built-in-only fixes only required a kernel rebuild and `update.img` repack.

## Findings

### Corrected: ARM zImage text offset

The 6.1 vendor tree carries an RK3506-specific ARM zImage text offset:

```make
textofs-$(CONFIG_CPU_RK3506) := 0x00108000
```

The 6.12 and 6.6 trees were missing this entry and fell back to the generic ARM
`0x00008000` offset. This is an early boot setting used by the compressed ARM
kernel before normal device-tree, clock, GPIO, or LED drivers run, so it fits the
observed failure mode where the board never reached normal Linux-visible boot
behavior.

Changes made:

- Added `textofs-$(CONFIG_CPU_RK3506) := 0x00108000` to
  `kernel-6.12/arch/arm/Makefile`.
- Added the same RK3506 text offset to `kernel-6.6/arch/arm/Makefile`.
- Rebuilt 6.12 and verified `arch/arm/boot/compressed/.head.o.cmd` contains
  `-DTEXT_OFFSET=0x00108000`.

### Corrected: remove diagnostic DTS and LED checkpoints

Temporary LED checkpoint edits were useful to locate how early the failure was,
but they are not part of the production boot path.

Changes made:

- Restored `RK_KERNEL_DTS_NAME="rk3506b-luckfox-lyra-ultra"` in
  `device/rockchip/.chips/rk3506/luckfox_lyra_ultra_ubuntu_emmc_defconfig`.
- Removed the raw GPIO1_A0 checkpoint from `clk-rk3506.c`.
- Removed the GPIO probe LED checkpoint from `gpio-rockchip.c`.
- Restored the 6.1 vendor PVTPLL mux write in `clk-rk3506.c`.

### Verified: board DTS parity

The active Lyra Ultra board DTS files are identical between the known-good 6.1
tree and the 6.12 tree:

- `rk3506b-luckfox-lyra-ultra.dts`
- `rk3506-luckfox-lyra-ultra.dtsi`

This rules out a board-level DTS typo as the current 6.12 boot blocker.

### Verified: RK3506 clock driver parity

After removing temporary diagnostics, `kernel-6.12/drivers/clk/rockchip/clk-rk3506.c`
matches the 6.1 vendor file. The 6.12 config has the required clock support:

- `CONFIG_CPU_RK3506=y`
- `CONFIG_CLK_RK3506=y`
- `CONFIG_ROCKCHIP_CLK_PVTPLL=y`

This rules out the missing RK3506 CRU driver as the remaining blocker.

### Verified: rootfs module match

The current Ubuntu rootfs image contains matching modules for the rebuilt 6.12
kernel release:

- kernel release: `6.12.85-dirty`
- rootfs module directory: `/lib/modules/6.12.85-dirty`
- OS after the latest rootfs hook pass: `Ubuntu 24.04.4 LTS`

Ethernet, eMMC, GPIO LEDs, and the heartbeat trigger are built in or enabled in
the 6.12 config:

- `CONFIG_MMC_DW=y`
- `CONFIG_MMC_DW_ROCKCHIP=y`
- `CONFIG_STMMAC_ETH=y`
- `CONFIG_DWMAC_ROCKCHIP=y`
- `CONFIG_LEDS_GPIO=y`
- `CONFIG_LEDS_TRIGGER_HEARTBEAT=y`

The rebuilt rootfs also carries the updated RK3506 USB2 PHY module alias:

```text
alias of:N*T*Crockchip,rk3506-usb2phyC* phy_rockchip_inno_usb2
alias of:N*T*Crockchip,rk3506-usb2phy phy_rockchip_inno_usb2
```

### Corrected: RK3506 ARM cache/timer Kconfig drift

The 6.12 and 6.6 Rockchip ARM Kconfig files were selecting several old ARM
cache/timer options unconditionally. The 6.1 vendor tree only selects them for
RK30xx/RK3188-class SoCs, not RK3506.

Changes made:

- Restored the 6.1 conditional selection logic in
  `kernel-6.12/arch/arm/mach-rockchip/Kconfig`.
- Applied the same correction to `kernel-6.6/arch/arm/mach-rockchip/Kconfig`.
- Rebuilt 6.12 and verified the generated RK3506 config now has:
  `# CONFIG_CACHE_L2X0 is not set`, with only `CONFIG_ROCKCHIP_TIMER=y` and
  `CONFIG_ARM_ARCH_TIMER=y` left enabled for the RK3506 timer path.

### Active isolation: 6.12 kernel with known-good 6.1 DTB

The 6.1 image that booted on the Lyra Ultra used a 38 KiB generated DTB:

- DTB hash: `bb4ee7cb6cf069e4fb97ad67acdd416eca80441f8bf666f0f28cdc4845e160c8`

The current 6.12 build generates a larger 53 KiB DTB from the current RK3506 DTS
sources:

- DTB hash: `59ad168ab75938a7415883d7624226d8f9707f7337ac5188e170b66f033d28c6`

The size difference is explained by vendor DTC behavior. The 6.1 tree has
Rockchip-specific options:

- `CONFIG_DTC_OMIT_DISABLED=y`
- `CONFIG_DTC_OMIT_EMPTY=y`

Those options add `-Wnode_disabled` and `-Wnode_empty` to the 6.1 DTC flow and
the vendor `scripts/dtc/checks.c` uses them to omit disabled and empty nodes from
the generated DTB. The 6.12 tree does not currently have this vendor DTC omit
support, so it keeps disabled RK3506 peripheral nodes in the DTB.

Changes made:

- Added `CONFIG_DTC_OMIT_DISABLED` and `CONFIG_DTC_OMIT_EMPTY` to
  `kernel-6.12/drivers/of/Kconfig`, defaulting on for RK3506 Rockchip builds.
- Added the matching DTC flags to `kernel-6.12/scripts/Makefile.dtbs`.
- Ported the vendor `node_disabled` and `node_empty` DTC checks into
  `kernel-6.12/scripts/dtc/checks.c`, with a root-node guard for 6.12's
  `drivers/of/empty_root.dtb` build target.
- Applied the same DTC omit support to the 6.6 tree.
- Rebuilt 6.12 and verified the generated native 6.12 Lyra Ultra DTB is now
  byte-identical to the known-good 6.1 Lyra Ultra DTB:
  `bb4ee7cb6cf069e4fb97ad67acdd416eca80441f8bf666f0f28cdc4845e160c8`.

The earlier isolation image manually packaged the rebuilt 6.12 kernel with the
known-good 6.1 Lyra Ultra DTB/resource. The current image supersedes that by
generating the native 6.12 DTB/resource through the corrected 6.12 DTC path. If
it still does not boot, the blocker is in the 6.12 kernel path before userspace.

### Corrected: RK3506 GMAC binding/data

The Lyra Ultra Ethernet node uses:

```text
compatible = "rockchip,rk3506-gmac", "snps,dwmac-4.20a"
```

The 6.12 `dwmac-rk.c` driver had no RK3506 compatible entry or RK3506 GRF data.
That meant Ethernet would not bind even if the kernel reached userspace.

Changes made:

- Ported the RK3506 RMII mode, RMII speed, clock-selection, and register map
  callbacks from the working 6.1 driver into
  `kernel-6.12/drivers/net/ethernet/stmicro/stmmac/dwmac-rk.c`.
- Added the 6.12 OF match entry:
  `rockchip,rk3506-gmac`.
- Rebuilt 6.12 and verified `vmlinux` contains `rockchip,rk3506-gmac`,
  `rk3506_set_to_rmii`, and `rk3506_set_clock_selection`.

### Corrected: RK3506 USB2 PHY module binding

The Lyra Ultra USB2 PHY node uses:

```text
compatible = "rockchip,rk3506-usb2phy"
```

The 6.12 USB2 PHY driver had no RK3506 match data. The 6.1 vendor driver has
additional RK3506-only direct PHY tuning fields that are not present in the
smaller 6.12 driver, so this first 6.12 port is the safe binding/register-data
subset rather than a full vendor-driver transplant.

Changes made:

- Added RK3506 USB2 PHY port and charger-detection register data to
  `kernel-6.12/drivers/phy/rockchip/phy-rockchip-inno-usb2.c`.
- Added the 6.12 OF match entry:
  `rockchip,rk3506-usb2phy`.
- Added a guard so SoCs without a valid 6.12 `clkout_ctl` register do not write
  to offset zero during `clk_usbphy_480m` prepare/unprepare.
- Rebuilt the module and rebuilt the Ubuntu rootfs so `/lib/modules/6.12.85-dirty`
  contains the updated module and generated alias files.

### Corrected: RK3506 GPIO V2.2 controller support

The Lyra heartbeat LED is a normal GPIO LED:

```text
compatible = "gpio-leds"
gpios = <&gpio1 RK_PA0 GPIO_ACTIVE_HIGH>
linux,default-trigger = "heartbeat"
```

The 6.1 vendor GPIO driver recognizes the RK3506 GPIO controller version ID
`0x010219C8` as `GPIO_TYPE_V2_2` and routes it through the Rockchip V2 register
write/read path. The 6.12 and 6.6 GPIO drivers only recognized `GPIO_TYPE_V2`
and `GPIO_TYPE_V2_1`; a V2.2 controller would fall back to the V1 register
layout. That can prevent GPIO registration/control on RK3506 and directly
explains a boot where Linux may be running but the heartbeat LED never starts.

Changes made:

- Added `GPIO_TYPE_V2_2` to `kernel-6.12/drivers/gpio/gpio-rockchip.c`.
- Treated all `gpio_type >= GPIO_TYPE_V2` controllers as V2-layout controllers
  for register reads, writes, bit writes, IRQ register access, and debounce.
- Restored the vendor pinctrl direction handoff before GPIO direction changes,
  using the 6.12 chip-plus-offset pinctrl API.
- Applied the same V2.2 recognition and V2-layout handling to the 6.6 GPIO
  driver, using 6.6's older GPIO-number pinctrl API.
- Rebuilt 6.12 successfully and compile-checked the 6.6 GPIO object.

### Corrected: keep RK3506 on the generic DT machine path

The working 6.1 RK3506 boot does not match
`arch/arm/mach-rockchip/rockchip.c`: its machine compatible table does not
include `rockchip,rk3506g-demo-display-control` or `rockchip,rk3506`. That means
the working boot uses the generic DT machine path.

During 6.12 bring-up, RK3506 compatibles had been added to the Rockchip-specific
machine table. That made 6.12 take `rockchip_dt_init()` and call into the
Rockchip suspend init path, which is not what the working 6.1 RK3506 boot did.

Changes made:

- Removed the RK3506 compatibles from
  `kernel-6.12/arch/arm/mach-rockchip/rockchip.c`.
- Changed `kernel-6.12/arch/arm/mach-rockchip/pm.h` so
  `rockchip_suspend_init()` is a real declaration only for RK3288 PM builds and
  an inline no-op for RK3506.
- Changed `kernel-6.12/arch/arm/mach-rockchip/Makefile` so the RK3288 suspend
  objects are not built for RK3506.
- Applied the same RK3288-only PM object/stub cleanup to the 6.6 tree.
- Rebuilt 6.12 successfully and verified the FIT kernel hash changed.

### Corrected: match 6.1 PSCI machine-object build behavior

The working 6.1 ARM Makefile only builds `mach-rockchip` when `CONFIG_ARM_PSCI`
is not enabled:

```make
ifndef CONFIG_ARM_PSCI
machine-$(CONFIG_ARCH_ROCKCHIP) += rockchip
endif
```

The 6.12 and 6.6 trees were still building `mach-rockchip` unconditionally.
After correcting this in 6.12, the rebuilt 6.12 `vmlinux` no longer contains
the Rockchip machine descriptor symbols `rockchip_dt_init` or
`rockchip_smp_ops`; it keeps the same generic DT/PSCI path as the working 6.1
RK3506 boot.

Changes made:

- Wrapped `machine-$(CONFIG_ARCH_ROCKCHIP) += rockchip` with the 6.1
  `ifndef CONFIG_ARM_PSCI` guard in `kernel-6.12/arch/arm/Makefile`.
- Applied the same guard to `kernel-6.6/arch/arm/Makefile`.

## Remaining 6.1-to-6.12 Deltas

These remain different from the vendor 6.1 tree, but they are not the strongest
explanation for a pre-LED, pre-network boot failure.

### Vendor Rockchip cpufreq/OPP/SIP stack

6.1 has these enabled and 6.12 does not:

- `CONFIG_ARM_ROCKCHIP_CPUFREQ=y`
- `CONFIG_ROCKCHIP_OPP=y`
- `CONFIG_ROCKCHIP_SIP=y`
- `CONFIG_ROCKCHIP_CPUINFO=y`
- `CONFIG_ROCKCHIP_SYSTEM_MONITOR=y`

The RK3506 CPU OPP table references Rockchip PVTPLL/OPP metadata, so these may
matter for CPU frequency scaling, voltage/OPP selection, thermal behavior, or
longer runtime stability. They are less likely to explain failure before normal
clock and GPIO init. If the text-offset image boots but has cpufreq, thermal, or
stability problems, port this vendor stack next.

### FIQ debugger console

6.1 has Rockchip FIQ debugger support enabled, while 6.12 does not. This affects
`console=ttyFIQ0` and early serial diagnostics. It should not be required for
Ethernet/eMMC boot, but it would improve bring-up visibility once the UART cable
arrives.

### MMC host driver differences

The 6.12 `dw_mmc-rockchip` driver differs from 6.1's vendor driver. This could
matter if the kernel reaches eMMC probe but cannot mount `/dev/mmcblk0p3`.
It is not the first suspect for a no-LED/no-network boot because the heartbeat
LED and clock init should happen before rootfs mount.

## Hardware Result

The 6.12 image `update-6.12-ultra-gpio-v2_2-gmac-usbphy-psci.img` reached
heartbeat LED and responded to ping over Ethernet on the Luckfox Lyra Ultra.
That confirms the port now gets through kernel boot, eMMC rootfs mount,
userspace startup, GPIO LED trigger, and GMAC network traffic.

SSH did not come up on that image. Rootfs inspection showed `openssh-server` and
`ssh.socket` were present, but `/etc/ssh/ssh_host_*` host keys were absent. A
first-boot service now generates SSH host keys before `ssh.socket`/`ssh.service`
and explicitly enables both SSH activation paths.

The follow-up SSH-hostkey image booted to Ubuntu 24.04 and Ethernet/SSH, but
the minimized 1.5 GiB root filesystem filled immediately. The base Ubuntu
tarball's `/etc/rc.local` path also created a 1 GiB `/swapfile`, which could
consume the remaining space before package operations or first-boot resize
completed. The current rootfs now ships as a 2 GiB ext4 image, removes the old
swapfile path, and replaces the old `S40resize2fs` flow with a grow-only
`lyra-rootfs-grow.service`.
